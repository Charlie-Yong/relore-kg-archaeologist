# HistoryKG 期末答辩老师高频追问 10 问应答小抄（通俗直观版）

> 用途：供汇报人（P4）在课堂现场应对老师连续追问使用。每题均按「先讲一句话大白话结论 + 举出精确实验数字 + 诚实说明边界」组织，不背代码也能讲清楚。

---

### Q1：你们这和直接拿大模型切块做纯文本 RAG（向量/BM25 检索）本质差在哪？真需要建图吗？
- **大白话结论**：纯文本 RAG 只能“按字面关键词找片段”，跨不出断掉的链接；知识图谱能“顺着关系网跨过好几层实体找全证据”，而且能分清谁是官宣、谁只是口头提了一嘴。
- **实测数字**：
  - 在同样用 `deepseek-v4.1-flash-1017` 的 **8 道全新未见题**上，纯文本 `A_v2` 只有 **63.6%（14/22）**，而图谱版 `B_v2_fast` 拿到 **90.9%（20/22，高出 27.3 个百分点）**。
  - 最典型的例子是未见题 `U2`（Issue #224 为什么拒绝加密载荷）：纯文本检索只捞到提问者关贴，漏掉维护者“超出范围 + 建议继承 Signer”的回复，直接 **0 分（0/3）**；图谱靠 `Decision -[ABOUT]-> Issue #224` 拿到 **满分 3/3**。同样在第二仓库 `blinker` 的 `BL2` 题上，纯文本 **0/3**、图谱 **3/3**。
- **诚实边界**：如果只是一个没有提交演化历史、没有多步因果链的纯百科文档问答，轻量 RAG 确实就够了，不需要重度建图；图谱的收益主要来自多跳追踪与强弱证据核验。

---

### Q2：期中我问过，如果不建图，直接用 Codex / Claude Code 这种强通用 Agent 去翻仓库、联网查 GitHub 不也能做吗？你们比它强在哪？
- **大白话结论**：强通用 Agent 就像“临场雇一位程序员手工翻网站”，多半能查对，但每问一题要花 4 分钟、读几百万个字，甚至会中途抽风；HistoryKG 是“提前把账本整理成索引字典”，**准确度更稳的同时快了约 70 倍**。
- **双口径公平数字（我们不挑好看数字汇报）**：
  - 按**全部 6 道共同题**看，Codex `E` 组得 `10.5/17（61.8%）`，因为有 2 题被它的浏览器工具封装字符串截断没吐出正文；
  - 哪怕把那 2 道工具故障题去掉，**只算它正常作答的 4 题**，它确实能拿到 **95.45%（10.5/11）**，但中位等待时间是 **262.6 秒（4 分多钟）**，单题输入消耗高达 **150 万到 443 万 Tokens**；
  - 同一组 4 题上我们的 `B_v2_fast` 拿到 **11/11（100%）**，全部 6 题也是 **17/17（100%）**，中位延迟只有 **3.40 秒**，且每一句话都硬绑定本地冻结偏移索引，现场演示不会断连或临场超预算。

### Q3：为什么你们图谱里既有 `ClaimsToClose` 又有 `Closes`？这不是重复吗？
- **大白话结论**：一点不重复，这是特意为了**防止“作者嘴上说关了、实际根本没被采纳”**。
- **解释口径**：在 GitHub 上，任何人发 PR 都可以自己在正文里写 `Closes #146`，只要文本里出现，正则就能抽成 `[文本声称] ClaimsToClose`（就算那个 PR 后来被拒绝关掉没合入，这句话也还在）。而 `[官方API] Closes` 是调用 GitHub 官方只读 GraphQL 接口查出来的**平台确认关闭边**。我们还会再用 `MergedAs` 和 `git diff-tree`（`[Git实证]`）校验提交真正落地了。
- **实测区分**：`itsdangerous` 主仓冻结于 GraphQL 接入前，保留了 `ClaimsToClose`（32 条）；第二仓库 `blinker` 完整跑通新接口后，真实同时捕获了 **5 条 `Closes`** 和 5 条 `ClaimsToClose`。

---

### Q4：你们说知识抽取从 v1 升级到 v2 提升了，到底改了什么？有没有夸大？
- **大白话结论**：主要靠给 `PROMPT_V2` 加三条规矩——（1）踢掉 Dependabot 等机器人自动升版本号的流水账；（2）踢掉只报 Bug 不讨论取舍的普通帖；（3）分清“某人提议（proposed）”和“维护者拍板采纳/拒绝（accepted/rejected）”，并保留完整原因引号。
- **双数据集真实数字**：
  - 在原先 30 条 `orig30` 上：精确率 **40.0% → 66.7%**，F1 **0.4651 → 0.6061**，理由覆盖 **29.4% → 52.9%**，机器人误报 **8 → 0**；
  - 在**完全不相交、从未看过的新抽样 20 条 `heldout20`** 上：机器人误报也 **6 → 0**，误报总条数从 **8 降到 3**，理由覆盖从 `3/8` 升至 `5/8`（TP 同为 9，说明没有靠瞎删来换精确率）。
- **诚实局限**：两个集上都有召回天花板（`FN = 8` 和 `5`），主要是长讨论里隐含维持现状的决定容易漏；另外 20/30 条样本下的 95% Wilson 置信区间还较宽，且 `heldout20` 有 1 条跨仓归属未定条目按严苛口径标明。

### Q5：为什么在未见题上，你们的“快速模式（`B_v2_fast`）”反而比“深度思考（`B_v2_deep`）”得分还略高（90.9% vs 88.6%）？
- **大白话结论**：因为前面知识图谱的子图检索已经把答案需要的“核心证据材料”挑干净了，模型直接看材料归纳最准确；如果强迫它开启长链深度思考，反而会脑补过度把无关旁支文件也写进清单里。
- **证据支撑**：未见题 `U4`（PR #405 修改了哪 2 个文件）上，`B_v2_fast`（显式 `reasoning_effort="none"`）准确列出目标文件拿 **3/3**，而 `B_v2_deep` 多带入了关联旁支文件被裁判扣了 0.5 分（`2.5/3`），在代码题 `U7` 上深度思考还花了 **50.55 秒**（`fast` 仅 `3.35s` 同样满分）。

### Q6：既然图谱这么强，为什么未见题 `U6` 和 Blinker `BL3` 都只拿到一半左右的分数（1/3 和 1/2）？
- **大白话结论**：这暴露了我们目前一个真实的短板——**仓库里的“维护分支标签（例如 `2.1.x`）”和“GitHub 官方正式发布（例如 `2.2.0`）”在摘要里混排在一起，系统还不够擅长帮模型一眼分清**。
- **改进思路**：只需要在 Neo4j 写库阶段给 `Release` 节点加一个 `is_official_release` 标志并按发布时间排序过滤即可解决；我们特意没有为这两道未见题临时改代码打补丁，把问题诚实保留在报告里。

---

### Q7：你们说能扩展到大规模仓库，真的试过几万节点不崩吗？
- **大白话结论**：确实测过，而且第一遍在 `5x` 规模真崩过一次！因为当时我们把全图塞进 Neo4j 的**一个大事务**里提交，在 1 GB 内存限制下直接报 `MemoryPoolOutOfMemoryError`（超过 `716.8 MiB` 上限）。
- **工程解决与复测数字**：后来我们改成每 `500/1000` 条记录分批提交事务、分批清理删除，并用默认 `cypher_subgraph`（只查所需子图）+ FTS5 + SHA 点查差异替换原先全库导出 `snapshot`。改完之后顺利跑通 **`10x` 规模（40,670 个实体、116,740 条关系、74,170 条来源）**：`snapshot` 从 2.11 秒暴涨到 **23.52 秒**（11.16 倍），而 `cypher_subgraph` 仅从 0.56 秒增至 **3.02 秒**（**提速 7.80 倍**）。

---

### Q8：如果开源仓库每天有新 PR 和新提交，你们难道每次都要推倒整张图重算吗？
- **大白话结论**：不用推倒重建，我们实现了 `apply_delta` 时序增量演化，只对比删改并局部 `MERGE` 更新变化的部分。
- **实测数字**：我们将 `ItsDangerous` 按真实时间切分为 `T1(≤2018-10) → T2(≤2021-05) → T3(全历史)` 三步演进：`T1`（2,528 来源 / 1,741 实体 / 3,375 关系）零未来泄漏，`T2` 准确激活 `PR #152` 演进；在 `T3` 新增 `2,614` 来源、`1,209` 实体、`4,621` 关系时，`apply_delta` 仅耗时 **2.60 秒**（对比全库从头写入 **3.09 秒**提速 **1.19 倍**），更重要的是读回整库的密码学指纹 **`fingerprint_equal = true` 100% 严格等价**，没有增量漂移。同时 `eval_incremental.py` 已针对 `/releases` 仓级聚合接口实现逐条目时间裁剪，彻底消除了早期回放时间泄漏。

---

### Q9：你们所有的优化和提示词是不是只针对 `ItsDangerous` 做了过拟合特调？
- **大白话结论**：不是。我们专门用代码扫描确认 `historykg/` 下已经清除了所有旧仓库特化硬编码（`grep` 为空），改为纯靠语料 IDF 自动算关键词权重；然后**不改一行源码**直接对第二个开源库 **`pallets-eco/blinker`** 完整跑了六阶段构建、抽取和评测。
- **迁移数字**：`blinker` 自动构建出 **3,396 个实体、5,958 条关系**（还顺带抓出 5 条官网 `Closes` 边），跨仓 QA 准确率从纯文本的 **69.2%（9/13）** 提升到 **92.3%（12/13，中位 1.48 秒）**。

---

### Q10：今天现场演示万一教室断网、或者您随便问一个库里根本没有的功能，系统会怎样？
- **大白话结论**：两手都有兜底——（1）问库里不存在的假前提（例如 `U8` 虚构模块 `encrypted_payload` 或 `BL6` 移除 `Signal`），`B_v2_fast` 会在不到 1 秒内直接诚实拒答，**不编造任何一个 PR 号或 SHA**；（2）万一教室网断或百炼接口卡住，一条 `HISTORYKG_REPLAY_FILE` 环境变量命令即可秒切验证态离线回放展示真实记录，保证展示不断档。
