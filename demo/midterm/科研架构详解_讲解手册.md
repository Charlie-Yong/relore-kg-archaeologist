# 期中汇报｜科研架构详解与讲解手册

配套《期中汇报_科研架构详解版_20261108_完整版》，共 12 页。此版把各环节的输入、处理、输出、所用技术和边界展开，现场可自行选择讲解重点。每页还附有 PowerPoint 演讲备注。

项目当前代码见 [historykg](../../historykg/)，每页图底部列出对应模块。示例和实验引用已有记录，不把旧版实验分数写成新版采集器的成绩。

## 1｜问题与目标

开源项目的“为什么”分散在 Issue、PR、评审、提交、源码和发布说明中。只看某一时刻的代码，往往只能知道现在实现了什么；只做关键词搜索，又容易漏掉跨记录的关联。

系统希望将有限范围内的项目历史组织为**实体、关系和可回溯证据**：用户输入一个公开 GitHub Python 仓库链接，系统采集并冻结来源、抽取决定与理由、建立图谱；随后用户提问时，系统从同一来源池中找依据，返回结论、原文片段和链接。

当前范围是每次一个公开 GitHub Python 仓库；选择上限明确，不代表覆盖全部项目历史。

## 2｜总架构：构建链和问答链

上半部分是构建链：

1. **采集与冻结**：发现仓库，按规则选取讨论；分别读取讨论原文与代码历史，并保存数据版本、出处和缺口。
2. **知识抽取与校验**：GitHub / Git 提供明确元数据事实；DeepSeek 从讨论中提取结构化决定、状态与理由。程序校验字段、归属及原文引文。
3. **图谱与索引**：将合格的实体、关系、来源和证据纳入统一数据契约；Neo4j 保存图，SQLite 或 PostgreSQL 保存讨论检索索引。

下半部分是问答链：用户问题进入词法检索；讨论索引与共同来源池的排名按 RRF 合并；可选的图路径扩展补充有关联的来源；统一回答器根据原文片段输出结论和引文。

图和检索按 dataset_id 隔离。图扩展返回的证据必须映射回当前冻结来源池，不会因为图上多了一条边就凭空创造原文。

## 3｜采集：从 URL 到冻结来源

**输入。** 一个公开 GitHub Python 仓库 URL。程序规范化 owner/repo，检查仓库公开性和语言。

**选取。** 讨论候选按更新时间整理，优先已合并 PR；识别 PR 标题和正文里指向本仓库的明确引用，再用近期 Issue 补足。引用可以是 #编号、owner/repo#编号或完整链接。仓库外引用保留并标记范围，不会自动变成当前项目的事实。

**读取。** GitHub REST 读取 Issue / PR 正文、普通评论、评审和行内评论。根据 Link 头继续翻页。每次请求前记录已用请求数，响应后保存内容和必要分页信息；恢复时重用已保存的成功页。读不到的部分记录 unread 或其他缺口。

**输出。** SourceDocument 保存来源类型、规范化文本、URL、作者、时间及文本哈希。SourceUnit 把同一线程的正文、评论和评审组织为一个讨论单元。运行还记录选取理由、覆盖、gaps 和请求数。

**默认上限。** course_small_v1 每类候选最多 100 条、讨论最多 40 个、默认 PR 最多 20 个、GitHub 请求最多 300 次；分页、失败和重试都计入请求数。实际选中量可以少于上限。

代码：[发现与选单](../../historykg/ingest/discovery.py)、[GitHub 读取](../../historykg/ingest/github.py)、[采集入口](../../historykg/collector.py)。

## 4｜代码与演化：为什么需要 Git 和 AST

选中的已合并 PR 提供 merge_commit_sha 和合并时间。代码模块据此读取提交及其父提交，通过 Git 差异识别新增、修改、删除、重命名的 Python 文件，再读取相应前后版本的源码。

File 的身份包含**提交 SHA 和文件路径**：同一路径在不同提交下可以是不同的文件快照。删除文件读取父版本；前后文件关系需要同路径或明确重命名等依据。

Python AST 对已保存源码做静态解析，提取函数定义、导入、符号和源码位置。由此形成诸如 Commit—Touches→File、File—Defines→Function、File—Imports→File 以及文件版本之间的 ChangesTo。它不执行目标仓库的源码。解析失败、目标不在已采文件中或导入无法唯一解析时保留缺口。

默认 profile 最多读取 40 个相关提交和 24 个文件状态；这些数字是上限，不是系统必须凑满的数量。

代码：[代码采集](../../historykg/code/collect.py)、[AST 分析](../../historykg/code/ast_analysis.py)。

## 5｜模型抽取：从一段讨论得到结构化候选

**输入。** 一份冻结讨论单元、可选主体目录、任务提示和模型配置。长文本按设定上限拆分，相邻块重叠 400 个 Unicode 码点；每块记录实际可见原文和范围。

**候选字段。** 模型返回 target_repo、subject_id、action、status、statement、rationale、理由状态以及结论、理由、归属的原文引文。主体只能选择已有目录中的对象；动作与状态使用约定枚举。

**程序校验。** Pydantic 检查 JSON 字段、非空和理由约束。明确给出理由时必须同时提供理由及证据；原文没有给出理由则使用 not_stated，存在歧义可用 unclear。程序进一步核对仓库归属和引文是否在可见原文中。

**分类与输出。** 可以明确归属本项目且验证通过的候选生成 Decision、Evidence 以及 ABOUT、EVIDENCED_BY 等关系；外部项目的改动保留为 external_project 候选，不挂为本地决定；主体无法唯一确定时保留 unresolved 和缺口。引文重复时使用位置或相邻上下文消歧，不能任选一次。

大模型不是事实数据库：结构化格式和引文定位只是程序检查的一部分，不能单凭格式正确就断定语义正确。

代码：[抽取阶段](../../historykg/extract/stage.py)、[模型与证据说明](../../docs/p4/models.md)。

## 6｜证据链：怎样从结论回到原文

SourceDocument 的身份由规范仓库、来源键和文本 SHA-256 等内容形成；dataset_id 基于仓库、profile 和 job 标识生成。数据集身份与文本哈希分别承担版本和内容核验作用。

Evidence 最少包含 source_id、start、end 和 quote。位置使用规范化后文本的 Unicode 码点，区间左闭右开。校验式为：

    source.text[start:end] == quote

同一 quote 出现多次时，需要足够的相邻上下文或有效位置；引文还要落在模型本次实际可见的来源块内。回答器输出的每条 claim 必须关联可定位证据，最终页面才能显示来源。

导入前还检查文本哈希、数据集和仓库一致性、来源清单、图谱实体及关系端点。**引文能定位证明原文确实存在；引文是否足以支持结论仍需语义评审。**

示例中，PR #6133 的测试调整理由引文位于 [282,352)，另一段项目归属引文位于 [204,281)。出处、作者与具体证据见 [P4 模型验证记录](../../deliveries/P4/2026-10-30/model_validation.json)。

## 7｜图谱 Schema：对象和关系的方向

常用节点包括 Project、Issue、PullRequest、Commit、File、Release、Developer、Function、Decision 和 SourceDocument。示意图上的主要方向为：

| 关系 | 方向 | 事实依据 |
|---|---|---|
| Authored / Merged | Developer → PullRequest | GitHub PR 作者和合并者元数据 |
| MergedAs | PullRequest → Commit | PR 合并元数据 |
| Touches | Commit → File | Git 差异与版本化文件快照 |
| Defines | File → Function | AST 定义与源码位置 |
| ABOUT | Decision → Project / Issue / PR / File | 已验证的主体归属 |
| EVIDENCED_BY | Decision → SourceDocument | 可定位的来源证据 |
| ClaimsToClose / Closes | PullRequest → Issue | 前者为文字声明；后者需要官方关闭事件支持 |
| ReachableIn | Commit → Release | Git 可达性证据 |

Release 对 PR 的文字提及，只说明有提及；提交是否在该版本中可达需要另外验证。图谱写入 Neo4j 前检查实体、关系类型、端点与证据；不同 dataset_id 的记录隔离。

代码：[关系端点契约](../../historykg/contracts.py)、[图谱导入](../../historykg/graph/store.py)。

## 8｜问答：两路检索与图扩展

问题先解析关键词、项目内讨论编号、GitHub URL、主体名称和别名。讨论索引按标题、正文和显式编号检索；共同来源词法适配同时覆盖讨论、源码、提交、发布说明和 API 原文。

两个来源排名使用 RRF 融合。某条来源在各排名中的贡献为：

    score(source) = Σ 1 / (60 + rank)

系统从显式主体和已命中来源对应的实体中选择种子。B 组可以从同一检索种子扩展图路径：默认最多 8 个种子、3 跳、50 条路径。路径再映射回当前冻结来源及证据，不引入其他数据集原文。

合并去重后最多取 40 个来源候选；共同渲染器按上下文顺序与预算裁剪，最终规范 JSON 默认最多 12,000 Unicode 码点。统一回答器据此生成 claims 和 quote，程序再定位引文并附出处。A 组和 B 组的关键差别是是否启用图扩展，其他来源池、问题、回答器和上下文预算保持一致。

代码：[检索与融合](../../historykg/query/retrieval.py)、[查询服务](../../historykg/query/service.py)、[回答器](../../historykg/llm/answer.py)。

## 9｜运行、状态、恢复与预算

P1 的唯一流水线按 discover、collect、code、extract、validate、index_graph 六阶段运行。每个作业保存 job_id、当前阶段、覆盖计数、缺口、用量和检查点。页面刷新读取同一个 job；失败或阻塞后，恢复入口可利用已完成阶段和已冻结的成功分页。

状态要区分：

- ready：约定阶段完成，实际模型抽取、图谱和检索等发布条件满足。
- partial：已有可用产物，但存在已记录的覆盖或处理缺口。
- blocked：请求额度、凭据或其他可恢复条件阻塞。
- failed：程序、存储或模型失败，尚无可发布产物。
- unsupported：输入不在当前支持范围。

GitHub 请求预算包含分页和重试；模型使用共享持久账本，在请求前预留额度，失败、重试和未知用量保留记录。ready 是运行状态，不是知识质量评分。

代码：[作业编排](../../historykg/pipeline.py)、[模型账本](../../historykg/llm/budget.py)。

## 10｜实验设计与结果边界

**抽取实验。** 对 30 个测试讨论单元，按独立模型参考评估结构化决定。旧版结果 Precision 0.568、Recall 0.962、F1 0.714；参考中 15 条明示理由覆盖 13 条。参考是模型银标，不等同于人工金标准确率。

**问答 A/B。** 20 道测试题使用相同冻结来源、问题、模型、提示、最终上下文预算及评审配置。A 只用共同检索，B 从同一检索种子增加图扩展。旧版事实覆盖分别为 A 0.600、B 0.740；15 道可配对题的平均覆盖差为 0.157，95% 描述性 bootstrap 区间 [-0.122, 0.457] 跨零。无依据断言率分别为 A 0.026、B 0.043，不能只讲覆盖改善而忽略代价，也不能宣称统计显著优势。

**版本说明。** 这些数字来自 2026-10-30 旧版检索实验。当前采集器及讨论排序已经变化，尚未对新版本重跑同一 A/B，因此不得将旧分数直接作为新版成绩。

依据：[正式汇总](../../evaluation/results/formal_summary.json)、[评测说明](../../docs/evaluation.md)、[现行查询方法](../../docs/graph_query.md)。

## 11｜小范围真实开发例：Flask PR #6133

该开发回归使用早期冻结的 PR 正文和 API 原文；没有重新核对完整讨论，单元状态为 partial。

- PR 原文说测试调整是为了适应尚未发布的 Werkzeug，理由引文位置为 [282,352)。
- 同一 PR 的另一段写明 client.query 新增于 Werkzeug PR #3219；系统将它保留为外部项目候选，不把它挂成 Flask 的新增决定。
- 实际抽取记录包含 2 条本地 Decision 和 1 条 external_project 候选；实际回答返回 2 条 claims，每条均有一段可定位原文证据。

该例用于解释“理由、归属、证据”如何沿流程保留，不能当作正式测试准确率。现行采集器 2026-11-08 在线采集的 2 个讨论、13 条来源、10 次 GitHub 请求，是**另一项独立小样验证**，与 #6133 旧例不是同一次运行。

依据：[PR 原文](https://github.com/pallets/flask/pull/6133)、[开发回归记录](../../deliveries/P4/2026-10-30/handoff.md)、[原文与两条回答](../../deliveries/P4/2026-10-30/model_validation.json)、[采集器变更记录](../../03_范围与契约变更记录.md)。

## 可能被问到的问题

**采集器和 ReLore 是什么关系？** 早期原型用 ReLore 验证方案；当前课程版在 HistoryKG 内实现有限采集、分页、快照、恢复及讨论检索。早期来源和许可证保留在[第三方说明](../../THIRD_PARTY_NOTICES.md)。

**为什么引文正确仍可能回答错误？** 引文校验只验证文本和位置存在。结论可能曲解原文、混淆项目归属、把提议当成已接受，或把关闭声明当成关闭事件；这些属于语义与事实支持问题。

**图谱相比直接把原文交给模型多做了什么？** 它显式保存对象和关系，允许从一个命中对象沿可核查关系寻找相关来源；回答仍以原文证据为依据。图扩展可能增加覆盖，也可能引入噪声。

**更换仓库一定能完整运行吗？** 入口支持公开 GitHub Python 仓库，系统自动选取有限来源；权限、API 额度、文件编码、资料缺失和预算都会影响完成度，需检查实际 status 与 gaps。

**新版做过哪些验证？** 现行采集器做过 Flask 在线小样和 SQLite / PostgreSQL 回放；两份公开冻结数据包可在当前版本重建图及检索。新采集和新排序尚未重跑完整旧版模型 A/B；页面中的旧数字有明确版本标识。
