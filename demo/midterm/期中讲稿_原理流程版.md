# 期中汇报讲稿｜原理与流程

对应《期中汇报_原理流程版_20261108》，8 页。正文安排 **4 分 45 秒**，留 **15 秒**切页和缓冲；随后预留 **2 分钟提问**。具体语速以小组试讲为准。

## 第 1 页｜封面｜0:00–0:20

我们想回答一个问题：一段代码为什么会这样改？理由分散在 Issue、PR、评审和提交里。我们的项目从公开仓库链接出发，整理这些历史记录，让答案能回到原文。

## 第 2 页｜全流程｜0:20–0:55

整个系统有四步。第一步采集讨论和代码历史；第二步从原文中抽取决定和理由；第三步把对象和关系组织成图谱；第四步根据问题检索相关资料，生成带出处的回答。这四步使用同一批冻结来源。

## 第 3 页｜采集｜0:55–1:30

系统先确认仓库公开且包含 Python。讨论侧用 GitHub 接口读取 Issue、PR、评论和评审；代码侧通过 Git 和 Python AST 获取提交、文件、函数和版本事实。材料保存原文、链接、时间及缺口。已读页面和请求次数也会记录，中断后可以续采。默认最多处理 40 个讨论单元、300 次 GitHub 请求。

## 第 4 页｜知识抽取｜1:30–2:10

讨论是自然语言，所以我们让 DeepSeek 先输出结构化候选，包括主体、动作、理由和引文。例如这里的 Flask PR 说，调整测试是为了适应尚未发布的 Werkzeug。程序再核对字段、项目归属和引文位置。原文没有说明理由，就记录为未说明；能找到引文，也仍要检查结论的语义是否被支持。

## 第 5 页｜建图｜2:10–2:50

图谱用节点表示对象，用边表示有依据的关系。比如一个决定关于哪个 PR，PR 对应哪个合并提交，提交触及哪个文件。决定还连接到来源原文。PR、提交和文件关系来自 GitHub 元数据与 Git，决定来自模型抽取。Neo4j 保存这些节点和关系，导入前检查关系端点与证据。

## 第 6 页｜问答｜2:50–3:30

用户提出问题后，系统先根据关键词和讨论编号检索冻结来源，再根据需要沿图里的关系补充相关事实。选出的原文片段交给统一回答器，输出结论和可定位的引文。证据不足时显示缺口。图路径和引文帮助我们核对答案，但不能自动保证模型结论正确。

## 第 7 页｜小范围真实示例｜3:30–4:25

看 Flask PR 6133 这个开发回归。原文说，调整测试是为了适应尚未发布的 Werkzeug。模型返回两条结论，并为每条保留可定位的原文证据。第二条结论还区分了项目归属：client.query 是 Werkzeug 的方法，不应挂成 Flask 的新增方法。

这个例子使用 2026 年 10 月 30 日冻结的 PR 正文和 API 原文，只覆盖部分来源；它说明系统怎样处理一段材料，不代表正式测试准确率。

## 第 8 页｜小组分工｜4:25–4:45

P1 负责数据与集成，P2 负责图谱与查询，P3 负责代码与演化，P4 负责前期调研、架构与原型，以及采集和模型，P5 负责原型与展示，P6 负责独立参考和实验。六个角色共同完成从仓库链接到有出处回答的流程。

## 两分钟提问准备

每题准备约 15–25 秒；按老师的问题选答。

**1. 知识图谱在这里起什么作用？**

它把讨论、决定、提交、文件与来源按有依据的关系连接起来。回答跨资料的问题时，系统能从命中的对象沿关系找到相关材料，并保留证据路径。

**2. 大模型和图谱分别做什么？**

大模型把讨论整理成决定、理由等候选，也根据检索到的原文组织回答；图谱保存经检查的实体和关系，支持按关系查找资料。模型使用的是现成服务，我们没有训练基础模型。

**3. 怎么降低模型编造或归属错误？**

要求模型给出逐字引文，程序核对原文位置和项目归属；找不到或不唯一的内容记录为缺口。定位正确只说明引文存在，结论是否成立还要看引文是否支持它。

**4. 采集架构从哪里来？**

早期原型用 ReLore 验证过思路。课程版按作业范围实现了自己的采集模块：直接读 GitHub，控制选取范围与请求数，保存原文快照和续采进度。原型来源及许可保留在仓库里。

**5. 目前验证到什么程度？**

旧版在 Flask 完成过真实模型抽取和有出处问答。新版采集器已在线采集两个 Flask 讨论，并用公开冻结数据重建图谱和检索；新版还没有重新完成完整模型实验。今天示例是旧版开发回归的已保存结果。

**6. 换一个仓库可以吗？**

入口支持公开 GitHub Python 仓库，每次处理一个仓库；系统自动选择有限来源。覆盖范围受数量和请求上限约束，不能声称覆盖整个仓库的全部历史。
